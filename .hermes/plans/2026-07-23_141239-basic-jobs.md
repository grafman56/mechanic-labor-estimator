# Basic Source-Backed Jobs Implementation Plan

> **For Hermes:** Implement this plan task-by-task with failing tests before each production change.

**Goal:** Complete the basic live repair-job set so each estimate uses the exact selected vehicle manual, exact published labor row, and only source-supported procedure requirements.

**Architecture:** The selected manual remains the authority. The backend discovers exact labor rows and procedure evidence on demand; the UI displays the source wording verbatim and never invents side, bank, parts, labor, or access distinctions. Ambiguous source results remain unavailable until the user selects an exact published row or source path.

**Tech stack:** Python 3 standard library HTTP/HTML parsing, local `http.server` API, browser ES modules, `unittest`, Node test runner.

---

## Current baseline

- Branch: `hermes/feasibility-prototype`
- Working tree: clean at plan time.
- Manual-selected live lookup works without VIN.
- Common jobs already represented in `src/tier1-jobs.js`:
  - front struts; rear struts/shocks; alternator; starter; radiator;
  - wheel bearing/hub; serpentine belt; spark plugs; valve-cover gasket;
  - timing belt; water pump.
- `/api/live-job-rows` now exposes source row text and hours; `/api/live-job-labor` accepts an exact `source_row`.
- Existing hard-coded MDX package/access recommendations are legacy VIN-only behavior and must not be copied into manual-selected live estimates.

## Non-negotiable rules

1. The source manual’s scope wording wins. `Left Side`, `Right Side`, `Front Bank`, `One Bank`, and `Both Sides` have distinct meanings.
2. Do not map a generic `One Side` or `One Bank` row to a left/right or front/rear claim.
3. Do not use labor tables as proof that a gasket, fluid, seal, or bolt is required. Procedure evidence is required.
4. No generic fallback labor, parts, access recommendation, or extrapolated rate.
5. Store only small derived results/source URLs if caching is later added; do not mirror manuals.

**Objective:** Give each listed Tier-1 job a source-backed path or an explicit source-limited result.

**Files:**

- Modify: `tools/manual_lookup.py`
- Test: `test/test_operation_links.py`, `test/tier1-jobs.test.mjs`

**Method for each job:**
1. Use a real selected manual to inspect exact operation titles and labor rows.
2. Add a fixture with that source shape.
3. Run the fixture test RED before changing aliases/resolution.
4. Implement only exact aliases/path equivalence supported by the source.
5. Perform a real-source smoke lookup.
6. Add its result to the coverage matrix in README.

**Coverage matrix / acceptance criteria:**

| Job family | Required source behavior |

| Front struts | Show exact front/left/right/one-side/both-side rows as published. |
| Rear struts/shocks | Show exact rear/left/right/one-side/both-side rows as published. |
| Alternator | Select a single published replacement row; exclude overhaul rows. |
| Starter | Match `Starter Motor` and verify replacement row. |
| Radiator | Select exact replacement row. |
| Wheel bearing/hub | Keep `Front Suspension` and `Hub & Bearing Assembly` distinct; retain one/both side scope. |
| Serpentine belt | Accept equivalent duplicate source paths only when source row/hour agree. |
| Spark plugs | Same duplicate-path equivalence requirement. |
| Valve-cover gasket | Keep explicit front/rear bank rows distinct; use `One Bank` only when that is the manual’s exact wording. |
| Timing belt | Select only published `Replace`; do not silently add optional seals or water pump labor. |
| Water pump | Accept only equivalent engine/cooling paths with matching row/hour; reject a conflict. |

### Task 5: Add procedure-evidence extraction for each completed job

**Objective:** Start the smart layer without reintroducing hard-coded recommendations.

**Files:**

- Modify: `server.py`
- Modify: `app.js`, `index.html`
- Test: `test/test_procedure_evidence.py`
- Modify: `README.md`

**Step 1: Define the evidence contract**

```python
{
  "status": "available" | "unavailable",
  "items": [
    {
      "kind": "required" | "replace-if-removed" | "inspect",
      "label": "Intake manifold gasket",
      "reason": "Exact procedure sentence or table wording",
      "source_url": "https://lemon-manuals.la/..."
    }
  ],
  "reason": "No procedure evidence found."  # only when unavailable
}
```

**Step 2: Test first**

Fixtures must prove:
- explicit `replace gasket` becomes a `required` evidence item;
- `inspect` remains inspection only;
- bare labor data never creates a parts recommendation;
- an absent procedure yields unavailable, not a guessed list.

**Step 3: Implement a narrow first parser**

Use the selected exact operation path to locate its corresponding Repair and Diagnosis procedure. Extract only explicit requirement language; preserve URL and concise supporting text. Do not copy full manual text into project storage.

**Step 4: Roll out per job family**

Start with valve-cover gasket, timing belt/water pump, radiator, then the remaining basic jobs. Each family requires a real-source smoke test and one fixture before becoming available in the smart area.

**Step 5: Commit per family**

## Risks and tradeoffs

- LEMON navigation duplicates the same data under several paths. Deduplicate only identical source row text and hours.
- Some manuals will expose only generic `One Side` or `One Bank`; the product must preserve that limited wording.
- Procedure pages may be absent or incomplete. That means no smart recommendation, not a fallback recommendation.
- Some operation paths legitimately conflict. Require a manual operation selection rather than applying a heuristic.
